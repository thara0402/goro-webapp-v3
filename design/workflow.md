# 開発ワークフロー

このドキュメントは、開発工程と品質ゲートの定義です（GitHub Actions の定義ファイル `.github/workflows/` とは別物です）。

- このドキュメントの変更は人間が行う。カスタムエージェント（`architect` を含む）は編集しない。

## Quality Gates

アプリケーションの品質を保つため、コード変更はローカル検証と CI 検証の両方を通過してから完了扱いとする。

- Copilot による実装では、完了報告または Pull Request 作成前に、影響範囲に応じたテストをローカルで実行する。
- このリポジトリでは原則として `dotnet test src/goro-webapp/goro-webapp.slnx --no-restore` を実行し、失敗した場合は原因を修正してから完了報告する。
- テストの合計が 0 件の場合は成功とみなさない（依存関係が未復元の可能性がある）。`dotnet restore src/goro-webapp/goro-webapp.slnx` を実行してから再実行する。
- テストを実行できない場合は完了扱いにせず、実行できなかった理由と代替確認内容を明示する。
- CI ではテスト専用 GitHub Actions ワークフローを使用し、`pull_request` で .NET 10 ソリューションの restore、build、test を実行する。
- Azure App Service へのビルド・デプロイワークフローは `main` ブランチへの push で起動し、デプロイ用ビルド内で test を成功させてから publish・デプロイへ進む。テスト専用ワークフローは `pull_request` 専用とし、PR マージ後にテストとデプロイが並列実行されないようにする。

## AI Agent Workflow

Issue またはチャットの依頼を起点とした AI 駆動開発では、`.github/agents/` のカスタムエージェントで工程と役割を分担する。工程管理はオーケストレーターが担い、各担当エージェントはサブエージェントとして自分の工程だけを実行する。

### 適用範囲

- Issue とチャットのどちらを起点にする場合でも、`src/goro-webapp/` と `design/`（このドキュメントを除く）の変更は `orchestrator` を使って行う。
- `README.md`、`.github/`（CI を含む）、このドキュメントの変更は、担当エージェントの編集範囲外のため、例外として既定のエージェント（カスタムエージェントを選択しない状態）で行ってよい。例外かどうかは変更するファイルの場所だけで判断し、`src/goro-webapp/` 内の軽微な変更も例外にしない。
- カスタムエージェントの選択は人が行うため、指示書だけでは強制できない。アプリケーションの変更を含む PR では工程実行記録を必須とし、記録がない PR はマージしないことで担保する。
- 例外の範囲は、ローカル検証で委任とスキルの読み込みが動作することを確認した後に見直す。

### 実行環境

- ローカル実行：GitHub Copilot App または VS Code で `orchestrator` を選択して開始する。
- クラウド実行（将来）：GitHub Copilot Cloud Agent に Issue を割り当てる際に `orchestrator` を選択する。Cloud Agent での担当エージェント呼び出し、コミット、PR 作成の動作は導入時に検証する。

### エージェントと権限

| エージェント | 役割 | 編集してよい範囲 | 主なツール |
| --- | --- | --- | --- |
| `orchestrator` | 工程管理、担当への委任、ゲート判定、完了報告 | なし（ファイルを編集しない） | read、search、agent、todo、GitHub の読み取り用個別ツール |
| `architect` | Issue と `design/` の照合による個別設計の具体化と設計書更新、アーキテクチャ判断の要否の識別 | `design/` 配下（`design/workflow.md` を除く） | read、search、edit |
| `developer` | 承認済み設計に基づく本体コードの実装と、受け入れ条件に対応する Unit テストの追加・更新・実行 | `src/goro-webapp/` 配下（`goro-webapp/` と `goro-webapp.Tests/`） | read、search、edit、execute |
| `reviewer` | 設計・受け入れ条件・テストとの整合性レビューと、テストの独立した再実行 | なし（読み取り専用。コマンドは参照系と `dotnet test` のみ） | read、search、execute |

- 実装とテストは同じ担当が一体で変更する。コンストラクターなどの変更がテストのビルドに影響するため、別担当に分けると実装工程が完了できなくなるためである。
- テストの独立性は、`reviewer` が受け入れ条件ごとのテストの有無を判定し、`dotnet test` を自ら再実行することで確保する。
- 小規模なリポジトリのため、全体構造を決めるアーキテクトと個別要件を具体化する設計担当者を `architect` 1 つが兼ねる。`architect` の判断は次の 2 区分に分ける。

| 区分 | 例 | 扱い |
| --- | --- | --- |
| 個別設計 | Issue に伴う `design/spec.md`、`design/data-model.md` の機能仕様・データモデル・画面や処理の変更 | `architect` が決定し、設計書を更新する |
| アーキテクチャ判断 | 技術・パッケージの選定、認証方式、Cosmos DB 全体のデータ配置方針、層構造や依存方向の変更、性能・セキュリティ・拡張性などの品質特性の方針変更 | `architect` は確定せず、選択肢と推奨案を示して未決事項として報告し、人間が決定する |

- `architect` は Issue で求められていない全体構造の変更を行わない。

- `orchestrator` はユーザーが明示的に選択して使用する。
- 担当エージェントはエージェント選択一覧に表示せず、`orchestrator` から呼び出す。
- 担当エージェントは `.github/copilot-instructions.md` の共通方針（設計書の確認、Secret 方針、テスト方針）に従う。

### 参照ドキュメントと参照スキル

各エージェント定義には「参照ドキュメント」と「参照スキル」のセクションを設け、「制約」には禁止事項のみを記載する。

| エージェント | 参照ドキュメント | 参照スキル |
| --- | --- | --- |
| `orchestrator` | `design/workflow.md` | なし（作業は担当エージェントに委任するため） |
| `architect` | `design/architecture.md`、`design/spec.md`、`design/data-model.md`、`design/gourmet.json` | `cosmosdb-datamodeling`、`microsoft-docs`、`microsoft-code-reference` |
| `developer` | 設計レポート、`design/architecture.md`、関連する設計書 | `dotnet-best-practices`、`csharp-async`、`dotnet10`、`csharp-mstest`、`microsoft-code-reference` |
| `reviewer` | 設計レポート、`design/architecture.md`、`design/spec.md`、`design/data-model.md` | `dotnet-best-practices`、`csharp-async`、`csharp-mstest`（レビュー基準として） |

- `.github/copilot-instructions.md` の「スキル」はリポジトリ全体のスキル一覧、エージェント定義の「参照スキル」は担当ごとの割り当てとする。スキルを追加・削除した場合は両方を更新する。
- スキルは関連すると判断されたときだけ読み込まれる仕組みであり、実行環境や `tools` の制限によっては読み込まれない可能性がある。そのため、参照スキルには `SKILL.md` のパスを記載し、該当する作業の前に `read` で直接読むよう指示する。
- 各担当エージェントの報告形式に「参照したスキル」を含め、スキルが使われたかを確認できるようにする。
- スキルが読み込まれるかは、導入時にローカル実行（VS Code / Copilot App）で検証する。読み込まれない場合は、実行環境のスキル用ツールを `tools` に追加する。

### 工程とゲート

```text
Issue 受付 → 設計（architect） → 設計承認ゲート → 実装・テスト（developer）
  → レビュー・テスト再実行（reviewer） → 完了報告 / PR → CI → 人間の承認・マージ
```

1. **Issue 受付**：目的、対象領域、受け入れ条件、変更してよい範囲、変更してほしくない範囲、検証観点を確認する。受け入れ条件がない、または判断できない場合は設計へ進まない。
   - **合格条件**：本文と全コメントを取得し、Issue 番号が対象と一致すること、応答に repository が含まれる場合は repository も一致すること、本文が存在すること、全ページの取得が完了していることを確認する。コメント 0 件も取得成功として扱う。合格した場合のみ取得状況を受付結果に記録し、本文と全コメントの原文を `architect` に渡す。
   - **停止条件**：取得前に利用不可と推測して停止しない。MCP ツール未提供、呼び出し失敗、結果の不一致・欠落・切り詰め・本文なしの場合は、実際に確認できた根拠を示して停止し、本文と全コメントの共有をユーザーに依頼する。別の MCP ツールや CLI で取得を代替しない。具体的な呼び出し手順は [orchestrator 定義](../.github/agents/orchestrator.agent.md) を参照する。
   - **受入シナリオ**：

     | ケース | 入力・状況 | 期待結果 |
     | --- | --- | --- |
     | 成功 | Issue とコメントを取得でき、識別情報・本文・全ページが検証できる | 受付結果に記録して設計へ進む |
     | コメント 0 件 | コメント一覧が空 | 0 件を記録し、正常に設計へ進む |
     | 複数ページ | コメントが複数ページにわたる | 最終ページまで取得・検証してから設計へ進む |
     | ツール未提供 | 利用可能ツール一覧に MCP 取得ツールがない | 一覧確認を根拠として手動共有を依頼し停止する |
     | 取得失敗 | MCP 呼び出しエラー、または取得結果の検証不合格 | エラー・不合格の内容を根拠として手動共有を依頼し停止する |
2. **設計**：`architect` が受け入れ条件と設計書の対応、設計変更の要否、影響範囲、アーキテクチャ判断の要否、未決事項を報告する。個別設計の変更が必要な場合は、実装前に `design/` を更新する。
3. **設計承認ゲート**：
   - ローカル実行では、設計結果を提示して必ず停止し、人間の承認を得てから実装へ進む。
   - Cloud Agent では停止せず続行し、設計判断を PR 本文に明記して、PR の最終レビューで承認する。
   - 未決事項（アーキテクチャ判断を含む）が残る場合は、どちらの環境でも実装へ進まず、人間の判断を待つ。
4. **実装・テスト**：`developer` が承認済みの設計に基づいて本体コードを実装し、受け入れ条件に対応するテストを追加・更新して、`dotnet test` がすべて成功するまで修正する。
5. **レビュー**：`reviewer` が `dotnet test` を自ら再実行したうえで、設計書、受け入れ条件、テストと差分の整合性を確認し、重大度付きで指摘する。テストが失敗した場合、または受け入れ条件に対応するテストがない場合は `blocking` とする。
6. **差し戻し**：テスト失敗や重大な指摘は該当する担当へ差し戻す。差し戻しは最大 2 回までとし、解消しない場合は作業を止めて人間に判断を求める。
7. **完了報告**：変更内容、設計変更の有無、テスト結果、レビュー結果、未確認事項を報告する。Cloud Agent では同じ内容を PR 本文に記載する。

エージェントによる「テスト済み」「レビュー済み」の報告は補助的な確認とし、最終的な品質ゲートは [Quality Gates](#quality-gates) の CI と人間によるレビュー・マージとする。

### オーケストレーションの誤りへの対策

`orchestrator` も AI であるため、担当の呼び出し忘れ、完了条件の誤判定、自分での実装を完全には防げない。次の多層の対策で発生の可能性を下げ、残った誤りは人間と CI で検出する。

| 対象 | 対策 |
| --- | --- |
| 自分での実装 | `tools` に `edit` と `execute` を含めない。`github/*` は許可せず、Issue・PR の読み取り用の個別ツールだけを許可する。呼び出してよいのは `architect`、`developer`、`reviewer` のみとし、組み込みの汎用エージェントを呼び出さない |
| 呼び出し忘れ | Issue の大小にかかわらず全工程を実行し、省略しない。工程を固定 ID の todo として作業開始時に登録し、担当の報告を受け取った工程だけを完了にする。完了報告に工程実行記録を必須とする |
| 完了条件の誤判定 | 工程ごとの判定を「必須見出しの有無」と「数値」で行う。テストは `reviewer` が報告した `dotnet test` の集計行（加工しない原文）で、失敗 0 件かつ合計 1 件以上の場合のみ合格とする（合計 0 件の実行を成功と誤認しないため）。判定できない場合は不合格として扱う |
| 設計書更新の漏れ | `reviewer` が、設計レポートで更新したとされる設計書が差分に含まれているかを確認する |
| 残った誤り | `.github/pull_request_template.md` の工程実行記録と各欄を、人間がマージ前に確認する。CI を必須チェックとする |

- 最重要ルール（自分で編集しない、工程を省略しない、テストの合否は `reviewer` の再実行結果で判定する）は、`orchestrator` の定義の冒頭と末尾の両方に記載する。
- 工程実行記録は次の形式とし、空欄や「未実行」の工程がある場合は完了報告を出さない。

```markdown
| 工程 | 担当 | 呼び出し回数 | 判定 | 根拠（報告の該当箇所） |
```

- `agents` による呼び出し先の制限、および GitHub MCP の個別ツール名が各実行環境で有効かは、導入時のローカル検証で確認する。ツールの実行自体を止めるフック機能は、検証後に採用を検討する。
